# Pi Travel 参考产品真实体验调研

> 调研对象：<https://www.pitravel.cn/plan?lang=zh-CN>  
> 调研日期：2026-07-16  
> 最近更新：2026-07-17  
> 调研方式：桌面端与 390×844 移动端真实浏览、创建杭州 2 日测试行程、查看地图/工作台/活动详情/候选推荐/便签工具  
> 文档状态：已合并到最终产品 Brief  
> 说明：本文只学习产品结构和交互原则，不复制对方代码、文案、图片或品牌资产。

## 1. 结论先行

Pi Travel 最值得学习的不是“无限画布”本身，而是它把地点卡片、相邻路段、地图和候选地点放进同一个直接操作闭环：用户点击一个活动，就能同时看到它在当天顺序、地图路线和地点详情中的位置。

SuperTravelAgent 不应改成 Pi Travel 的画布型产品。我们已经确认的“左侧历史旅程 + 中间对话与完整文字方案 + 右侧地图和工作台”更适合真实旅行方案阅读，也更能展示多 Agent、实时工具、来源和校验能力。正确方向是保留自己的产品骨架，吸收 Pi Travel 在创建聚焦、活动卡片、路线间隔、地图联动、地点详情和推荐发现方面的优秀做法。

## 2. 本次真实体验路径

1. 浏览首页的搜索创建、攻略解析和“我的计划”。
2. 进入结构化创建表单，测试目的地联想、日期区间、旅行偏好和智能规划。
3. 创建“杭州 2 日、美食与历史偏好”的测试旅程。
4. 查看按天活动列、活动间路线、右侧地图、路线标记和地图宽度调整。
5. 点击活动查看图片、评分、营业时间、简介、地址、电话和评价摘要。
6. 展开推荐地点区域，查看推荐、待计划、收藏及类型筛选。
7. 测试便签、清单、图库等画布工具。
8. 用 390×844 视口复查创建页和旅行规划页的移动端表现。

## 3. 值得借鉴的设计

### 3.1 创建阶段聚焦单一目标

- 首页第一屏只强调“去哪里”，主操作非常明确。
- 目的地、日期和偏好采用宽输入区、标签和弹层，学习成本低。
- 最近行程卡片直接出现在创建入口下方，方便继续浏览。
- 推荐行程可以承担示例入口，和我们已经确定的“案例预览与 Agent 回放”方向一致。

适配到本项目时，保留我们更完整的出发地、成人/儿童/老人、预算、节奏和约束，不能为了视觉简洁删掉 Agent 真正需要的输入。

### 3.2 活动卡片与相邻路段一起展示

Pi Travel 在相邻活动之间直接显示距离、预计耗时和交通方式。这比把路线信息藏在地图中更容易检查，也能立即发现折返和不合理时间。

建议在我们的每日工作台中采用以下纵向结构：

`活动卡片 → 路段信息 → 活动卡片 → 路段信息`

路段信息只显示用户决策需要的内容：交通方式、距离、预计耗时；详细路线继续由地图承载。工作台草稿拖动期间使用估算或旧结果，点击“应用修改”后再请求真实路线。

### 3.3 卡片、地图和详情三向联动

- 点击活动卡片，地图居中并高亮对应地点和路段。
- 点击地图标记，定位到对应日期与活动卡片。
- 地点详情用抽屉或局部详情面板展示，不污染紧凑活动卡片。

这与当前 Brief 的地图联动一致，但可以进一步补充“地点详情层”：活动卡片保持简洁；营业时间、地址、电话、图片、简介、游客评价（摘要）和可访问来源放在详情层。

### 3.4 推荐发现与候选池（调研建议已被后续决策覆盖）

Pi Travel 的“推荐”帮助用户发现未进入行程的地点，“待计划”承载用户已经接受但尚未排入某天的地点。这个状态区分比把所有内容都塞入一个候选池更清晰。

调研阶段曾建议保留两个状态：

- **推荐发现**：Agent 或数据源给出的建议，尚未被用户接受。
- **候选池**：用户明确保留、但暂不属于任何一天的活动。

后续为遵守 KISS 原则并减少状态膨胀，最终确认第一阶段只保留“候选”一个业务视图：Agent 为本次行程准备的备选地点直接进入候选池，不再区分“推荐发现/已收藏/候选池”。以后若引入登录和跨行程地点收藏，再增加全局收藏。

### 3.5 分日快捷优化

Pi Travel 在每天顶部提供路线优化入口，入口位置自然。我们可以借鉴入口，但继续执行已经确认的规则：

- 默认只优化该天的顺序、交通和时间。
- 执行前显示确认框，并提示时间可能变化。
- 用户手动标记的固定时间不可被移动。
- 不自动增加新地点；空档优先从候选池补充，候选不足则保留自由活动。

### 3.6 准备清单和旅行素材

Pi Travel 的清单、便签和图库说明，旅行规划完成后仍需要“出发前准备”和“旅行中记录”。当前项目已经实现行程/日期/活动级清单与备注，适合保留并整理为“准备清单”。图库不应在第一阶段复制成独立画布，可通过“旅行照片”入口进入现有 PowerPaint，避免重复建设。

### 3.7 攻略链接或截图导入

“粘贴攻略链接/上传截图 → 提取地点”很适合展示 Agent 的网页理解和多模态能力，但它涉及登录墙、反爬、版权、提示注入、OCR 误差和来源追踪，不能直接写入正式行程。

推荐作为后续阶段功能：

`链接或截图 → 安全抓取/OCR → 提取地点与建议 → 用户审阅 → 加入推荐发现或候选池`

第一阶段不做浏览器插件，也不允许解析结果绕过用户确认直接改变正式行程。

## 4. 不应照搬的设计

### 4.1 不用无限画布替换三栏结构

真实测试中，2 日行程已经出现大面积空白；行程达到 7 日后还会产生长距离横向移动。画布适合手工摆放，但不适合阅读完整交通、住宿、预算、提醒、来源和 Agent 结果。我们的中间文字方案与右侧工作台应继续并存。

### 4.2 不设置“手动规划/智能规划”双按钮

本项目的两个创建入口已经明确：完整结构化表单直接生成，或自然语言输入后生成/澄清。生成后再通过工作台人工修改。增加“手动规划”会和这套模型重复。

### 4.3 不接受过密行程

真实生成的杭州 2 日行程分别安排了约 7 个和 9 个活动，且缺少明确起止时间，难以证明可执行。SuperTravelAgent 必须继续按旅行节奏控制密度：普通用户每天 4～5 个正式活动上限，慢节奏更少，特种兵偏好才适当增加；吃饭另行穿插。

### 4.4 不把冲突信息当成确定事实

真实体验中，同一景点的卡片、路线文字和详情出现了票价、预约和营业时间冲突。这说明视觉完整不等于数据可靠。我们的字段级来源、优先级、冲突处理、最终 Schema 校验和“待用户确认”必须保留。

### 4.5 不复制其移动端画布

390px 视口下，首页标签和卡片出现裁切，规划画布横向溢出，只能看到部分日期，顶部与地图工具拥挤。我们既定的移动端分区查看、当天上移/下移、备注、固定时间和删除更适合小屏。

### 4.6 暂不复制分享和 Chrome 插件

第一阶段已经明确不做分享。浏览器插件会显著增加安装、权限、兼容和审核成本，对核心“创建—修改—下载”闭环没有必要。

## 5. 与当前项目实现的对照

当前项目不是从零开始，已经具备若干可直接演进的基础：

- `TripWorkspace.tsx` 已能按日展示结构化活动、时间、停留时长、费用、相邻路线，并提供地点操作和地图回调。
- `TripProductTools.tsx` 已有清单、行程/日期/活动/地点级备注和文档导入导出基础。
- `ChatInterface.tsx` 已处理 `trip_day_upsert`、`trip_sources` 等 SSE 事件，可继续统一规划过程、最终章节和案例回放的事件归约。
- 当前样式已有地图/工作台结构与分隔条基础，但仍存在较多渐变、阴影和悬浮动效，后续视觉重构应收敛到已经确认的“湖山青绿”克制型产品语言。

因此，Pi Travel 的优秀体验主要是对现有组件做信息架构和交互升级，而不是推倒重写所有前端。

## 6. 第一轮建议决策包

建议把以下内容纳入产品方案：

1. 保留三栏与中间文字方案，不采用无限画布作为主界面。
2. 工作台活动之间增加路段条，显示交通方式、距离和预计耗时。
3. 增加工作台临时地点详情面板；活动卡片继续保持简洁，来源只在详情和正文来源列表中出现。
4. 第一阶段只保留一个“候选”视图，不再拆分推荐发现、收藏和候选池。
5. 每天增加“优化当天路线”快捷入口，复用固定时间与二次确认规则。
6. 将现有清单明确为“准备清单”，支持 Agent 生成和用户增删勾选。
7. 攻略链接/截图导入放入后续阶段，解析结果必须先由用户审阅。
8. 继续使用移动端分区界面，不采用横向画布。

## 7. 第二轮：右侧活动卡片与详情交互确认稿

### 7.1 当前实现位置

当前活动卡片已经位于右侧下方的旅行工作台中：右侧上方是地图，右侧下方是 `TripWorkspace`；工作台先显示“概览/行程”等一级内容，在“行程”中再按日期切换每天的活动卡片。正式改造继续使用这一结构，不把活动卡片移动到中间对话正文，也不复制 Pi Travel 的无限画布。

### 7.2 每日活动列表

每天采用以下纵向顺序：

`当日标题与优化入口 → 活动卡片 → 路段条 → 活动卡片 → 路段条`

- 活动卡片显示一张代表图片，并保留序号、活动名称、时间段、预计停留时长、地点类别、参考费用、固定时间提示、备注入口和必要操作。
- 卡片图片使用固定 4:3 缩略图，不显示轮播、图片来源文字或多图数量以外的图片操作；摘要、营业时间、地址、电话和游客评价不在活动卡片中展开，统一放入地点详情面板。
- 路段条显示交通方式、距离和预计耗时；存在可靠数据时可补充参考交通费用，失败时明确显示“路线信息待确认”，不绘制伪路线。
- 每天顶部提供“优化当天路线”，执行前必须由用户确认；优化可以调整当天顺序、交通和非固定时间，不改变日期、不新增地点，也不能移动固定时间。

### 7.3 地点类别

地点和活动使用稳定内部枚举，前端只显示中文：

- `attraction` → 景点
- `food` → 吃喝
- `transport` → 交通
- `hotel` → 住宿
- `shopping` → 购物
- `free_time` → 休息/自由活动
- `other` → 其他

类别通过统一图标、中文标签和低饱和浅色区分，不使用大面积高饱和色。类别用于筛选、候选池、地图标记和活动卡片，但不能替代活动名称。

### 7.4 地点详情面板与返回逻辑

- 点击活动卡片：选中对应 `activity_id/poi_id`，地图居中并高亮地点和相关路段，右侧下方工作台由原内容切换到地点详情面板。
- 点击地图标记：地图高亮标记，工作台切换到该活动所属日期，并打开同一份地点详情数据。
- 详情面板显示摘要、营业时间、地址、多张图片、电话、游客评价及必要来源；“游客评价”只展示 Agent 归纳后的简短摘要，不复制某个用户的原评论。
- 每个活动最多保存 3 张展示图片。活动卡片只使用其中 1 张代表图；详情面板在数据充足时使用 3 张图片，并采用一张主图与横向缩略图列表。
- 首张优先复用活动卡片代表图，切换图片不能改变地图选中状态或工作台返回上下文；不足 3 张时按实际数量展示，不得复制同一图片或使用无关图片凑数。
- 热门景点和餐厅通常能从网页搜索、百度地图、官网或图片服务获得图片，但仍可能因为地点冷门、接口限流、防盗链、授权字段不完整、海外数据覆盖或网络失败而没有可用图片，因此产品不能假设图片永远存在。
- 每个活动按实际可用数量展示 0～3 张图片：卡片最多 1 张，详情最多 3 张；无可靠图片或全部图片加载失败时，卡片与详情都不渲染图片区域，让文字内容自然补位。
- “游客评价”允许采用比票务和库存更宽松的参考资料，可以基于地图、可信网页和攻略中的公开反馈做概括；仍禁止脱离检索结果凭空生成具体体验、排队时长、服务事件或卫生问题。
- 评价资料过少时可以只展示一条保守摘要；没有任何可用反馈时隐藏“游客评价”区域，不生成空态卡片。
- 详情头部显示上下文路径，例如“第 2 天 / 灵隐寺”，并提供“返回第 2 天”和“行程总览”两个明确入口。
- “返回第 2 天”回到打开详情前所在的日期与滚动位置；“行程总览”回到工作台总览。
- 如果详情由地图标记打开，则优先返回用户最后访问的工作台视图；没有历史视图时返回该地点所属日期。
- 详情是工作台的临时子视图，不新增一个长期占位页签；地图始终保留在上方，用户关闭详情后不丢失当前缩放、中心点和日期筛选。

### 7.5 准备清单与备注

- 保留并优化现有准备清单，支持 Agent 根据票务、预约、天气、证件和装备生成初始项目，用户可以增删、勾选并补充自定义项目。
- 保留整体备注、每日备注和活动备注；活动备注继续绑定稳定 `activity_id`，活动移动日期、调整顺序或暂存候选池后仍保留。
- 活动卡片只显示备注存在提示和编辑入口，完整备注在编辑层或详情面板中查看，避免卡片被长文本撑高。

### 7.6 视觉与可访问性约束

- 右侧工作台继续使用“湖山青绿”的克制型产品视觉，类别色只承担识别作用。
- 详情切换使用 150～250ms 的状态过渡，不做弹跳或装饰性进场；系统开启减少动态效果时直接切换或仅淡入。
- “返回第几天”“行程总览”“优化当天路线”和活动操作均支持键盘聚焦，并提供清晰的悬停、聚焦、禁用和加载状态。
- 图片使用固定宽高比、`max-width: 100%`、`object-fit: cover`、懒加载和溢出裁切，不能撑破详情面板；加载失败后移除对应图片，全部失败则收起图片区域。
- 后端将活动图片建模为最多 3 项的有序 `images` 数组，并保存稳定 `cover_image_id`；前端卡片和详情必须消费同一数组，不能各自搜索出两套不同图片。

### 7.7 右侧下方工作台的信息架构

右侧下方不是只有“概览”和“每天行程”。正式工作台采用五个稳定主视图，地点详情是临时子视图：

1. **总览**：行程摘要、每天主题与活动数、预算摘要、整体备注、未应用修改状态和主要提醒数量。
2. **日程**：按日期切换每天计划，展示每日备注、单图活动卡片、相邻路段和“优化当天路线”。
3. **候选**：展示尚未排入某天的候选活动，支持按景点、吃喝、交通、住宿、购物等类别筛选，并可拖入或添加到指定日期。
4. **准备清单**：展示 Agent 生成和用户自建的票务、证件、天气、装备及其他待办，支持勾选、增删和关联到行程/日期/活动。
5. **提醒**：集中展示预约提醒和规划约束。预约提醒面向“需要用户后续处理的预约/购票事项”；规划约束面向“固定时间冲突、营业时间风险、路线过载、预算偏差和信息待确认”。

补充规则：

- 整体备注放在“总览”中，不再增加一个单独主页签；每日备注放在具体日期顶部；活动备注从卡片进入编辑，并可在地点详情中完整查看。
- 地点详情不会成为第六个长期页签。它从日程卡片、候选卡片或地图标记打开，关闭后返回来源视图和原滚动位置。
- 当前“预算”内容合并进总览并保留详细展开；“校验”合并进提醒中的规划约束；“来源”继续以中间最终方案底部的折叠来源列表为主；“地图分组”改为地图自身的日期/类别筛选，不继续占用工作台主页签。
- 候选活动直接承载 Agent 为本次行程准备的 7～15 个备选地点，第一阶段不再引入“推荐发现/已收藏/候选池”三套相近状态，避免用户判断成本和后端状态膨胀。
- 活动移入候选池时保留图片、备注和预约提醒，但清除所属日期、时间段与固定时间；重新排入某天后由系统建议时间，用户可以再次确认是否固定。

### 7.8 预约提醒边界

- 预约提醒不是订单或真实预约状态。系统只生成“需要确认/建议预约/建议购票”的行动项，不能显示“已预约”或“已购票”，除非用户手动标记已处理。
- 能获得可靠截止时间时显示具体日期时间和来源入口；无法确认时显示“建议出发前再次确认”，不得编造预约开放日或余票。
- 用户可以标记“已处理”、编辑提醒时间和添加备注；第一阶段不自动代购、不读取短信或订单，也不主动向外部平台提交预约。
- 提醒绑定稳定的 `activity_id`、`transport_option_id` 或 `hotel_id`。关联活动被移入候选池时提醒保留但标记“当前未排期”；活动被永久删除时同步删除关联提醒，并在删除确认中说明。
- 准备清单与预约提醒共用统一的后端行动项模型和完成状态，前端按类型分别呈现在“准备清单”和“提醒”视图，不能维护两套互相矛盾的数据。
- 第一阶段只提供应用内提醒：工作台角标及“提醒”视图展示待处理、临近和已逾期事项，并按目的地时区计算；不做操作系统推送、短信、邮件或日历同步。
