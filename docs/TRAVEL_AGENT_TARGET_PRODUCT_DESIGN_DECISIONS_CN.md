## 1. 目标与成功标准

SuperTravelAgent 不再只做“能够输出旅游文字的聊天 Demo”，而要形成一个用户可以真实使用、可以持续修改、并且能够体现多 Agent 工程能力的旅行规划产品。

产品需要同时满足两个目标：

1. **真实可用**：用户能够输入旅行需求、获得具有真实地点和路线的完整方案、修改日程、查看预算与提醒，并下载 Markdown/PDF。
2. **求职展示**：界面和代码能够清晰体现需求分析、资料研究、路线规划、实时核验、约束校验、多 Agent 协作、结构化数据和异常降级能力。

核心成功标准：

- 输出不再是通用模板，而是包含真实地点、真实路线和来源证据的结构化行程。
- 用户修改工作台后，地图、日程、预算和约束能够一致更新。
- 强实时信息不能由模型猜测；查询失败必须明确说明。
- 多 Agent 过程可观察、可折叠、可重试，但不展示模型原始思维链。
- 桌面端达到完整可用；移动端可查看并完成简单编辑。

## 2. 产品范围

### 2.1 第一阶段范围

- 国内旅行：优先形成完整闭环。
- 国际旅行：同时支持知识库中已有的热门城市和热门景点，能力允许降级，但不能伪装成已完整覆盖。
- 下载：Markdown 和 PDF。
- 历史记录：匿名设备身份 + 后端 SQLite。
- 分享、完整账户系统、跨设备同步：不进入第一阶段。

### 2.2 明确不做

- 不开发原生手机 App。
- 不展示模型原始 Chain of Thought。
- 不在第一阶段实现公开分享链接。
- 不用直线、虚线或模型编造的路径冒充真实道路路线。
- 不将估算数据包装成实时票价、实时库存或已确认预约。

## 3. 视觉方向

已选择 **A「湖山青绿」** 作为产品主题。

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| 深湖绿 | `#176B62` | 主操作、当前选中、关键进度 |
| 雾白 | `#F4F7F5` | 页面主背景 |
| 松墨色 | `#173D39` | 主文字、标题、深色图标 |
| 浅薄荷 | `#E4F0EC` | 次级面板、选中背景、轻提示 |
| 秋叶橙 | `#C87432` | 预约失败、超预算、时间冲突等警告 |

设计约束：

- 整体为明亮、克制、可信赖的工具型界面，不使用大面积紫色渐变。
- 主色用于主要按钮、选中状态和进度，不作为无意义装饰。
- 动效用于表达加载、完成、失败、折叠和联动状态，并支持 `prefers-reduced-motion`。
- 图片必须限制在所属容器内，采用固定宽高比、`max-width: 100%`、`object-fit: cover`、懒加载、溢出裁切和失败占位，不能撑破活动卡片、地图弹层或 Agent 最终方案区域。
- 正文图片和活动卡片图片下方不单独显示“图片来源”文字；来源、授权和更新时间仍保存在结构化数据中，必要时统一进入底部参考来源列表或导出附录。
- 桌面端为主；移动端保持可读性和简单编辑能力，不要求拖拽。

## 4. 总体信息架构

桌面端采用三栏布局。

### 4.1 左侧：历史与入口

- 新建行程。
- “旅行照片”入口，进入项目已有的照片 P 图工作台；其真实实现是 `/photo-editor` 路由中的 `PhotoEditor` 组件，并通过 PowerPaint 服务完成修复、扩图和局部重绘，不是 PowerPoint 演示文稿功能。
- 历史旅行行程列表。
- 当前行程和历史行程切换。
- “删除全部旅程”危险操作入口。点击后打开标准确认对话框，明确显示删除范围和“删除后无法恢复”，用户必须再次点击醒目的“永久删除全部旅程”才执行。
- 存在正在规划的行程时不允许清空全部旅程，先提示用户停止当前规划，避免清理历史时隐式取消运行中的 Agent。
- 用户画像、知识库、设置等已有必要功能可以保留。
- 历史记录由匿名设备身份关联，并保存至后端 SQLite；刷新页面、关闭浏览器或重启服务后仍可查看。
- 第一阶段不支持跨设备同步；未来登录后再迁移或合并匿名历史。

当前代码中 `Sidebar.tsx` 已经包含“旅行照片”、单个删除和“清空历史”的前端入口；重写时优先保留这部分能力，但清空动作必须从当前浏览器侧历史清理升级为后端匿名设备范围内的事务删除。

### 4.2 中间：创建、对话和最终规划

中间区域同时承担新建行程和修改当前行程，但不同状态下界面不同。

#### 新建状态

提供两个相互独立的创建入口，界面用“或”明确分隔，用户一次只使用其中一种方式：

1. **结构化表单入口**
   - 字段包括出发地、目的地城市、起止日期、成人数、儿童数、老人数、预算、旅行偏好等。
   - 表单旁边提供明显的“创建行程”按钮。
   - 表单填写完整后，点击按钮直接进入多 Agent 规划，不再要求用户重复输入自然语言。
   - 出发地、一个主要目的地城市、起止日期、成人/儿童/老人人数和全程总预算为必填项，旅行偏好为可选项。
   - 必填项缺失或格式错误时在字段附近就地提示，并禁用“创建行程”按钮，不使用弹窗打断填写。
   - 第一阶段只支持一个主要目的地城市，可以安排该城市周边一日游；暂不支持多个主要城市串联的长线行程。
   - 起止日期采用参考图所示的日历区间选择器：打开时定位当前月份，并按照用户所在时区将系统当前日期作为默认开始日期。
   - 当前时区显示在日历上方；默认开始日期使用清晰的选中样式，用户仍可切换月份或选择其他开始日期。
   - 用户选择结束日期后形成日期区间；结束日期尚未选择或区间超过第一阶段 1～7 天限制时，“确定”按钮保持不可用并就地说明原因。
   - 第一阶段只支持“确定日期”，不实现“大概几天”模式；过去日期禁用，允许选择系统当前日期当天出发。
   - 视觉结构参考用户上传的表单图：使用浅色页面背景和一个清晰的主内容面板，按“基础地点 → 日期 → 人数与预算 → 旅行偏好 → 创建操作”从上到下组织。
   - 出发地、目的地和日期采用宽输入控件；偏好使用可多选的紧凑标签；人数按成人、儿童、老人分组，不能因为参考图只展示目的地和日期而遗漏已确认字段。
   - 保留“湖山青绿”主题，不照搬参考图的紫色强调色；表单面板、输入控件和标签使用同一套边框、焦点、错误和禁用状态。
   - 参考图中的“手动规划/智能规划”不直接复制为两个并列按钮：本产品结构化表单只保留一个明确的“创建行程”主按钮，避免与下方自然语言创建入口产生第三种入口歧义。

2. **自然语言入口**
   - 表单下方提供对话输入框。
   - 输入框上方提供 3～4 个可点击示例。点击后先打开标准案例预览对话框，展示完整旅行需求、日期、人数、预算、偏好、案例特点和“开始体验”按钮，不立即发起真实规划。
   - 第一阶段前段允许只完成案例卡片和预览对话框，使用前端静态数据，不要求后端回放接口同时落地。
   - 完整形态使用已经真实跑通、人工验收并完成脱敏的固定案例包。用户点击“开始体验”后进入主三栏工作区，以“示例回放”模式按照录制顺序播放 Agent 阶段、工具摘要、降级、最终方案章节、地图和工作台展开，不能重新调用模型或实时 Provider 冒充回放。
   - 回放使用与真实 SSE 相同的前端事件归约器和事件结构；前端原型可以通过本地定时事件模拟，最终由后端 `/api/demo-cases/{case_id}/stream` 按 SSE 输出已录制事件。
   - 案例包至少包含 `case_id`、版本、展示摘要、完整输入、顺序事件、事件间隔、最终已校验 Schema、地点/路线、工作台状态、图片和来源快照。
   - 回放顶部持续显示“示例回放”标识，并提供暂停/继续、1 倍/2 倍速度、跳到最终结果和重新播放；尊重 `prefers-reduced-motion` 时只更新状态，不做逐字动画。
   - 示例回放不写入用户真实历史，也不允许直接保存对示例的修改；完成后可以点击“以此为模板创建行程”，把案例需求带入新建表单，再由真实 Agent 生成用户自己的行程。
   - 示例中的票价、库存、天气和营业时间必须标明“案例录制时信息，仅用于演示”，不得被理解为当前实时结论。
   - 用户输入旅游需求并发送后即可开始规划。
   - 信息完整时直接生成，不展示多余澄清。
   - 缺少会实质改变结果的关键信息时，在输入框附近展示澄清卡片，提供选项、自定义填写、跳过或采用默认值。
   - 澄清卡片用于理解真实意图，不进入最终规划正文。

#### 已生成状态

- 首次行程生成后，底部输入框默认隐藏，让最终规划成为视觉主体。
- 用户点击“继续修改”按钮后才显示输入框。
- 此时输入框的职责是修改当前行程，例如“把第二天的西湖换成宋城”。
- 当前对话与当前行程绑定；新建另一趟旅行应使用左侧“新建行程”。
- 如果修改输入中检测到新的目的地，系统不直接覆盖当前行程，而是弹出卡片提示“检测到新的目的地，是否创建新行程”。

### 4.3 右侧：地图与旅行工作台

- 上半部分为真实地图。
- 下半部分为可编辑旅行工作台。
- 新建状态和规划早期可以收起右侧，仅保留轻量状态提示；一旦进入 `completed` 或 `completed/degraded`，右侧真实地图与工作台容器必须完整展开，因为正式规划已经包含地点、景点、餐厅和分日活动，需要立即建立方案、地图和卡片之间的对应关系。
- “必须展开”约束的是界面结构，不意味着地图 Provider 永不失败：路线或地图加载失败时仍展开右侧，并显示已经解析的地点标记、工作台数据和明确的地图降级提示，不能因为某个地图接口失败而隐藏整个右侧。
- 中间与右侧之间增加可拖动的垂直分隔条，用户可以调整最终方案与地图/工作台的宽度；右侧内部仍使用水平分隔条调整地图与工作台高度。
- 分隔条需要键盘操作、最小/最大宽度约束和“恢复默认布局”，不能把中间正文或右侧活动卡片压缩到不可用宽度。
- 地图、工作台卡片和中间规划中的地点需要使用稳定的 `activity_id/poi_id` 双向联动。
- 选中任意地点后，其他区域应同步高亮并将地图定位到对应标记。

## 5. 多 Agent 规划体验

中间的模型响应分为两个层次：

1. **Agent 规划过程**：规划期间展开，完成后默认折叠。
2. **最终规划方案**：完成后作为主要内容展示。

- Agent 阶段进度、任务摘要、重试、降级和完成状态通过 SSE 持续推送并逐项展示。
- 最终规划也通过 SSE 渐进展示，但不能把未经完整 Schema 校验的模型原始 token 或半截 JSON 当作正式方案。后端先完成完整 Schema 校验，再把同一份已校验 Schema 按章节转换为 `final_plan_section` 事件流式推送，前端依次展开章节，最后收到 `trip_plan_completed` 后激活地图、工作台、下载和正式快照。
- Agent 过程完成后默认折叠，最终规划不能被过程日志淹没。

Agent 规划过程至少包含：

- 需求分析。
- 资料研究。
- 路线规划。
- 实时核验。
- 质量与约束校验。

每个阶段展示：

- 负责 Agent。
- 正在执行或已经完成的任务。
- 使用的工具或数据源。
- 结论摘要。
- 耗时。
- 等待、执行、成功、失败、重试等状态。

- Agent 或工具结果在界面中统一归纳为“成功、重试、降级完成、失败”四类中文用户状态；后端可以保留稳定英文枚举，前端不得直接显示 `planning`、`completed`、`cancelled` 等英文键名。
- 重试、降级或失败时只展示一行用户可理解的原因和实际处理结果，例如“天气接口超时，已改用近期天气资料”。
- 前端不展示异常堆栈、内部错误对象、Provider 密钥、请求签名、原始模型输出或其他实现细节；完整技术错误只进入受控后端日志。

限制：

- 只展示可验证的工作过程、工具调用摘要和结论，不展示原始思维链。
- 某个数据源失败时，允许阶段内重试或使用合规降级来源。
- 规划完成后默认折叠过程，用户可以重新展开查看。
- 最终规划不能被过程日志淹没。

建议的后端事件类型（尚待最终 Schema 确认）：

- `planning_stage_started`
- `agent_task_started`
- `tool_call_summary`
- `source_collected`
- `agent_task_retried`
- `planning_stage_completed`
- `planning_warning`
- `trip_plan_delta`
- `final_plan_started`
- `final_plan_section`
- `trip_plan_completed`

### 5.1 总控 Agent

采用一个真实的总控 Agent 负责整个规划生命周期，而不是只在前端模拟多 Agent 名称。总控 Agent 的职责包括：

- 接收表单或自然语言入口产生的统一旅行需求。
- 调用需求分析能力补齐和规范化约束，形成不可变的本次规划输入快照。
- 根据依赖关系生成任务图，并向专业 Agent 下发任务。
- 管理并行执行、串行依赖、超时、重试、降级和取消。
- 收集专业 Agent 返回的结构化结果、来源证据和失败原因。
- 解决重复地点、时间冲突、路线绕行、预算偏差和来源矛盾。
- 调用质量校验；必要时只重做存在问题的子任务，而不是重新运行所有 Agent。
- 汇总规划并输出统一的最终行程 Schema、Agent 过程事件和可下载内容。

总控 Agent 只能基于专业 Agent 结果和来源证据总结，不得补写未经核验的票价、库存、预约或其他强实时事实。

### 5.2 专业 Agent 与执行顺序

目标角色包括：

- 需求分析 Agent：提取城市、日期、人数、预算、偏好和硬约束。
- 目的地研究 Agent：检索景点、人文历史、当地体验和候选地点。
- 交通 Agent：查询去返程交通和城市内交通方案。
- 住宿 Agent：推荐住宿区域或酒店并评估通勤影响。
- 美食 Agent：检索当地特色美食和适合插入日程的餐厅。
- 实时核验 Agent：核验票价、库存、预约、天气、营业时间等，并执行分级降级策略。
- 路线规划 Agent：确定分日地点顺序、交通方式和真实路线。
- 预算 Agent：汇总参考价格、计算每日和全程费用并给出预算偏差提醒。
- 质量校验 Agent：校验时间、营业、路线、预约、预算和人群适配约束。

需求分析完成后，目的地研究、交通、住宿和美食任务可以并行；路线规划依赖候选地点，预算和质量校验依赖整合后的日程。总控 Agent 最后负责总结和输出整体方案。

### 5.3 Agent 重试与工具重试

- 单个专业 Agent 最多执行 2 次，即首次执行失败后最多再执行 1 次。
- Agent 重试和工具重试使用两套独立预算，不能在 Agent 每次重跑时重新获得完整工具重试次数。
- 总控 Agent 维护本次规划运行级别的重试账本，按 `provider + tool_name + normalized_arguments` 记录工具调用指纹、结果和失败类型。
- Agent 重跑时复用已经成功的工具结果，不重复调用相同接口。
- 相同工具参数已有进行中的请求时执行请求合并，不能并发重复发送。
- 支持幂等键、短期缓存和调用次数审计，避免“工具内部重试 × Agent 重试 × 总控重试”形成 9 次或更多重复调用。
- 认证失败、参数错误、明确无库存和配额耗尽等非瞬时错误不自动重试；超时、连接重置和明确限流等瞬时错误才进入工具重试策略。
- 专业 Agent 两次执行后仍失败时，总控 Agent 使用已完成的数据继续生成带缺失标记的完整行程；只有需求无法解析或最终 Schema 无法形成时才终止整次规划。
- 同一 Provider、同一参数指纹在一次规划运行中最多调用 3 次，即首次调用加最多 2 次瞬时错误重试。
- 工具调用达到 3 次仍失败且配置了备用 Provider 时，允许备用 Provider 使用同一语义参数再调用 1 次；备用调用也必须记录在同一运行级重试账本中。
- 遇到 HTTP 429 时优先遵循 `Retry-After`；其他可重试错误使用带随机抖动的指数退避。
- Agent 重跑不能重置上述工具调用次数，因此相同主 Provider 请求最多 3 次，而不是每次 Agent 执行都重新调用 3 次。

### 5.4 用户主动停止规划

- 规划过程中提供“停止规划”操作，并向总控 Agent 传播取消信号。
- 用户点击后立即停止，不再弹出二次确认框；按钮文案和悬停提示需要提前说明该操作不能继续恢复。
- 用户主动停止后，取消尚未开始的任务并尽力终止正在执行的 Agent 和工具调用。
- 删除本次 `run_id` 关联的 Agent 中间结果、阶段进度、未完成结构化结果、临时来源集合、事件缓冲和运行级工具缓存，不提供断点继续。
- 保留用户最初提交的表单或自然语言需求，用户只能基于原需求重新开始，也可以修改需求后重新创建。
- 停止后的行程记录标记为 `cancelled`，不生成正式行程快照，也不出现在可下载行程中。
- 停止操作只删除当前行程运行范围内的缓存；进程级或跨用户共享的 Provider 缓存继续按照自身 TTL 失效，不能被单个用户的停止操作清空。

### 5.5 页面刷新与 SSE 断线

- 页面刷新、浏览器临时关闭和 SSE 网络断线视为意外断线，不等同于用户主动点击“停止规划”。
- 后端总控 Agent 在客户端断开后继续执行，不因为 SSE 连接消失自动取消任务。
- 事件日志按 `run_id + event_id` 保留 5 分钟；前端携带最后收到的事件序号重连，并补发缺失事件。
- 5 分钟内重连时恢复 Agent 阶段进度；如果规划已经完成，则直接加载已保存的最终正式版本。
- 超过 5 分钟后不保证恢复完整流式事件；已经完成的最终规划仍从历史行程加载，仍在运行的任务通过当前状态快照重新显示进度。
- 高频文本片段保存在内存环形缓冲区中，并在 5 分钟后自动清理。
- Agent 阶段、工具调用摘要、运行状态和最后事件序号保存到 SQLite，用于页面重连时恢复结构化进度。
- 第一阶段不引入 Redis。服务器重启后不恢复高频文本流，未完成任务标记为“执行中断”并允许用户重新开始；已完成正式行程不受影响。

### 5.6 单设备运行并发

- 第一阶段每个匿名设备同一时间只允许存在一个 `planning` 状态的行程运行，避免多个行程同时消耗实时 Provider、网页检索和模型配额。
- 规划期间允许用户打开并查看其他历史行程；当前规划继续在后台执行，左侧历史列表持续显示生成中状态。
- 当前规划未结束时再次创建新行程，界面提示用户返回当前规划或先停止当前规划，不静默启动第二个并发运行。
- 后端以匿名设备标识建立活动运行唯一约束，前端按钮禁用只作为交互提示，不能作为唯一并发保护。
- 用户正在查看其他历史行程时，当前规划完成后不自动切换页面，避免打断阅读或编辑。
- 左侧对应行程显示“已完成”状态圆点，同时在桌面端展示约 5 秒的顶部轻提示“行程已生成，点击查看”；移动端使用页面顶部通知条。
- 第一阶段不申请系统级浏览器通知权限；用户点击站内通知后再跳转到新生成行程。

### 5.7 分层超时与完整性优先降级

按照用户提供的分层超时表执行：

| 层级 | 单次/单阶段时限 | 适用内容 |
| --- | ---: | --- |
| 快速工具 | 15 秒 | 地理编码、天气、地图路线 |
| 实时交易类工具 | 25 秒 | 车票、酒店、景点预约、库存 |
| 网页/攻略检索工具 | 35 秒 | 网页搜索、网页抓取、攻略解析 |
| 单个专业 Agent | 90 秒 | 研究、交通、住宿、实时核验 |
| 简单 Agent | 45 秒 | 需求分析、预算汇总、质量校验 |
| 整次规划软超时 | 180 秒 | 提示“仍在规划”，持续展示已经完成的阶段 |
| 整次规划硬超时 | 300 秒 | 5 分钟后结束剩余任务；能形成方案则输出并明确缺失，否则提示重试 |

- 工具时限按单次调用计算，仍受运行级工具重试账本和同参数调用上限约束，不能因为超时层级不同而额外获得重试次数。
- 达到 180 秒软超时后，界面继续展示已完成阶段和正在收尾的任务；后端停止启动低优先级扩展搜索，并降低非关键实时性的优先级。
- 软超时后的目标从“继续追求更多实时结果”切换为“优先形成完整、可用的旅行规划”：酒店、景点、天气、营业时间和参考价格可以使用已经取得的官网、地图、网页、攻略或知识库资料。
- 火车票和航班即使进入超时降级阶段也不得编造；查询失败时使用车站/机场与接驳框架、弹性首尾日和官方查询入口。
- 总控 Agent 在执行期间持续维护结构化规划草稿；达到 300 秒硬超时后取消未完成任务，并立即基于已完成结果和合规降级资料生成尽可能完整的最终 Schema。
- 硬超时结果只要满足以下最低标准，就保存为当前正式行程快照：旅行日期与人数等核心需求完整、每个旅行日期都有结构化安排、具有住宿区域建议、去返程交通框架、预算汇总和风险提醒。
- 具体酒店、真实路线几何、图片、实时票价或部分引用缺失时允许保存正式版本，但必须在对应章节给出降级或缺失提醒。
- 这类正式版本记录 `completion_mode = degraded`，供前端显示“已完成，部分信息待确认”，不能伪装成全部核验成功。
- 只有日期缺失、存在空白旅行日、无法形成去返程框架或最终 Schema 结构无效时，整次规划才进入 `error` 并提示用户重试。

## 6. 最终旅行规划内容

最终规划由结构化 Schema 确定性渲染，不依赖模型自由决定章节顺序。至少包含：

1. **目的地介绍**：城市概览、景点介绍、人文历史和旅行特点。
2. **去返程交通与票务**：从出发地到目的地以及返程的可选方案、时间、票价与核验状态。
3. **住宿建议**：推荐住宿区域或酒店、适合人群、通勤影响和价格参考。
4. **分日行程**：第一天、第二天、第三天等；景点、餐厅和当地特色美食自然穿插在时间轴中。
5. **费用与提醒**：每日小计、全程预算汇总、预约提醒、天气与携带物品提醒、风险提示。
6. **地图提示**：提醒用户可在右侧地图查看真实地点与路线。
7. **下载入口**：下载 Markdown 或 PDF。

### 6.1 行程长度与活动密度

- 第一阶段单次行程支持 1～7 天。
- 轻松、养生或不早起节奏：完整游玩日安排 2～3 个游玩活动，首个活动通常不早于 9:30，约 20:30 前结束。
- 均衡节奏：完整游玩日安排 4～5 个游玩活动，通常约 8:30 开始、21:00 前结束。
- 特种兵节奏：完整游玩日可以安排 6～7 个游玩活动，通常约 7:30 开始、22:00 前结束，但仍必须满足营业、预约、路线和交通约束。
- 到达日和返程日根据实际车次或航班时间自动减少活动，不为达到数量而强行填满。
- 活动数量仍需结合营业时间、地点距离、交通耗时、老人儿童同行等条件动态下调。
- 餐饮仍作为正式时间轴内容展示和参与路线计算，但不计入对应节奏档位的游玩活动数量。
- 候选池按旅行天数分档：1～2 天提供约 7 个候选活动，3～4 天提供约 10 个，5～7 天提供约 15 个。
- 历史行程不设置较小硬上限，左侧列表每页加载 20 条；第一阶段不提供归档和回收站。

每个景点或餐厅模块应尽量包含：

- 图片。
- 简介与文化背景。
- 建议到达时间和停留时长。
- 营业时间。
- 门票或人均消费。
- 是否需要预约以及建议预约时间。
- 前往下一地点的交通方式、距离和预计耗时。
- 中间最终规划正文中的对应事实保留来源数字角标；右侧工作台的活动卡片不展示来源状态、核验时间和数字角标。

## 7. 数据真实性、降级与引用

### 7.1 数据分级

#### 强实时数据

包括：

- 火车票票价、余票和车次状态。
- 航班票价、舱位与航班状态。
- 用户明确要求必须实时确认的其他长途交通票务数据。

规则：

- 优先调用实时接口或官方实时页面。
- 查询失败时不得由模型估算后冒充实时结果。
- 最终方案中明确显示“实时查询失败，请前往官方渠道确认”，并提供可访问来源或查询入口。
- 总控 Agent 汇总最终方案时不因为数据缓存到期而再次核验，直接使用本次规划中已经成功取得的查询快照，避免延长规划时间和重复调用工具。
- 火车票或航班实时查询失败时仍继续生成完整行程，但只保留推荐车站/机场、出发地与目的地、接驳建议和官方查询入口，不生成具体车次、航班号、时刻、舱位或票价。
- 当去返程时刻无法确认时，第一天和最后一天采用“抵达/离开时间待确认”的弹性安排，减少固定活动，避免虚构交通时间后造成整日计划失真。

#### 可降级数据

包括：

- 天气。
- 营业时间。
- 饭店人均消费。
- 酒店参考房价、房型和设施信息。
- 景点参考票价、预约规则和开放信息。
- 景点简介、人文历史、当地美食等资料。

规则：

- 优先实时或近期数据。
- 查询失败后可以降级使用官网、地图、可信攻略或本地知识库。
- 中间最终规划通过数字角标和底部参考来源列表说明出处；具体工作台活动卡片不强制展示来源和更新时间。
- 小红书等攻略可以用于经验信息和参考，但不能替代火车票、航班等强实时交通票务确认。
- 这些字段允许存在合理的信息时差，但必须来自真实来源，不能由模型凭空编造具体价格、库存或预约名额。

### 7.2 引用样式

- 正文使用无方括号的青绿色上标数字，例如“建议提前预约¹”。上标采用标准 `<sup><a>` 语义，不使用 Unicode 上标字符保存编号，以支持两位数以上编号、键盘焦点和屏幕阅读器。
- 引用在新标签页打开来源网址，并具有可见键盘焦点和屏幕阅读器标签。
- 整份行程采用全局连续编号，不按章节或日期重新编号。
- 相同来源在同一份规划中复用同一编号，避免重复编号。
- 最终规划底部生成完整、规范化的“参考来源”列表，并默认折叠隐藏；用户点击后展开。
- 角标悬停时建议展示来源标题、域名和更新时间。

### 7.3 第一阶段 Provider 与资料来源策略

- 火车票继续优先使用项目已经接入的 12306 MCP 等真实查询能力，并保留 Provider 接口，避免 Agent 直接依赖某一个工具的返回格式。
- 航班采用实时票务 Provider 或官方实时页面；查询失败时只能给出查询入口和失败提示，不能补写虚构航班、舱位或票价。
- 酒店和景点仍通过统一的 `Provider Adapter`、官网、地图和网络资料取得参考信息，但第一阶段不要求在最终汇总阶段再次核验价格、库存或预约状态。
- 酒店和景点的名称、区域、设施、开放规则、参考价格和游览经验，可以从官网、地图、网页搜索或可信攻略获取；小红书可用于体验与攻略参考。
- 上述酒店和景点参考资料可以直接用于最终规划的推荐理由、区域说明、设施信息、景点简介和游览建议，但必须随正文展示来源角标和参考状态，提醒用户这些内容仅供规划参考。
- 地图、普通网页搜索和小红书攻略提供的酒店房价、景点票价、开放时间和预约规则都作为规划参考，可以直接写入方案，但需要整体提醒用户实际信息以官方渠道为准。
- 酒店和景点可以展示“参考房价”“参考票价”“通常需要预约”等措辞；没有取得真实实时结果时，不得写“当前可订”“当前有票”“剩余名额”等库存性结论。
- 未配置第三方 Key 或实时 Provider 不可用时，系统仍生成完整行程；火车票和航班等强实时字段只能诚实显示查询失败和官方入口，不能填造库存或付款价格。
- 每条外部资料统一记录来源类型、来源网址、抓取或核验时间、适用字段和核验状态，供引用编号与最终校验 Agent 复用。

### 7.4 来源核验状态

后端结构化数据统一保留以下五种状态，用于总控 Agent 校验、来源列表和问题追踪：

1. `实时已核验`：来自实时 Provider 或官方实时页面，并在有效期内成功核验；第一阶段只有该状态可以支持火车票和航班的库存、余票或舱位结论。
2. `官方参考`：来自官方网站或官方公开资料，但不代表当前库存、余票或预约名额。
3. `地图参考`：来自地图服务中的地点、营业时间、评分、价格区间或路线等参考信息。
4. `攻略参考`：来自小红书、可信攻略网站或网页搜索结果中的经验性内容。
5. `待用户确认`：实时查询失败、来源互相冲突、来源过期或缺少足够证据，需要用户前往官方渠道再次确认。

- 状态和核验时间不作为右侧工作台活动卡片的可见标签；需要时可在底部参考来源列表或内部诊断信息中查看。无法获得精确发布时间时，只能记录本系统抓取或查询时间，不能伪装为来源发布时间。
- 同一活动的不同字段可以具有不同状态，例如景点简介为“官方参考”，门票库存为“实时已核验”，体验建议为“攻略参考”。
- 最终校验 Agent 必须阻止地图或攻略资料被错误升级为“实时已核验”。

### 7.5 来源优先级与冲突处理

事实字段使用以下优先级：

1. 实时官方数据与官方静态资料，同属第一优先级。
2. 地图资料为第二优先级。
3. 可信网页与攻略/小红书，同属第三优先级。
4. 本地知识库为最后优先级。

- 不同优先级来源发生冲突时，最终规划采用优先级更高的来源信息。
- 同一优先级来源发生冲突时，先选择发布时间或更新时间更新的来源。
- 无法可靠判断时间时，选择获得两个或以上独立同级来源共同支持的信息。
- 仍无法消除冲突时，总控 Agent 采用更保守、不容易误导用户的结论，并在底部参考来源列表保留其他冲突来源，不在正文中堆叠多个互相矛盾的说法。
- 主观体验、特色菜和游览技巧可以综合多个真实来源，不必强制只保留一个来源观点。

## 8. 地图：当前实现事实

截至 2026-07-16，项目当前地图并不是高德或 Mapbox 单一方案，而是混合实现。

### 8.1 前端

- 地图组件使用 `react-leaflet` + `leaflet`。
- 默认底图为 OpenStreetMap。
- 瓦片失败时依次尝试 Carto Light、OpenStreetMap FR 和一个直接拼接的高德瓦片地址。
- 当后端路线坐标系为 `BD09LL` 且配置 `VITE_BAIDU_MAP_AK` 时，切换到 `BaiduMapAdapter`，使用百度地图 WebGL JS API 展示国内地点和路线。
- 当存在国内路线但没有浏览器端百度 AK 时，当前实现不绘制混合坐标地图，只展示“国内地图暂不可显示”和地点列表。

相关实现：

- `frontend/src/components/MapComponent.tsx`
- `frontend/src/components/map/BaiduMapAdapter.tsx`

### 8.2 后端路线

- 国内路线：百度 DirectionLite，坐标系 `BD09LL`。
- 国际路线：OpenRouteService，坐标系 `WGS84`。
- 国内和国际根据 `scope` 选择不同 Provider。
- 路线逐段查询，并对路线和路线段进行缓存；失败时返回 `unavailable`，不生成伪造 geometry。

相关实现：

- `backend/services/route_geometry_service.py`
- `backend/services/route_providers/baidu.py`
- `backend/services/route_providers/openrouteservice.py`

### 8.3 当前配置观察

- 检测到后端示例环境中存在百度地图服务端 Key 配置。
- 未检测到前端 `VITE_BAIDU_MAP_AK` 文件配置，因此国内路线即使后端查询成功，也可能无法在浏览器中正常展示百度底图。
- 未检测到当前进程的 OpenRouteService Key；国际真实路线是否可用需要在启动环境中再次核验。
- 当前直接拼接高德瓦片地址不应被视为正式、稳定的高德 JS API 集成。

## 9. 地图服务费用调研

以下结论基于 2026-07-16 可访问的官方定价页面，正式发布前仍应重新检查。

### 9.1 高德地图

- 不是“完全免费且无限调用”。
- 认证开发者具有月配额和 QPS 配额；月配额内部分调用通过计费减免，超出后消耗流量包或账户余额。
- 官方页面当前列出的个人认证开发者驾车路径规划月配额为 150,000 次、QPS 为 3；JS 地图图面初始化月配额为 1,500,000 次、QPS 为 10。
- 基础 LBS 服务超额阶梯价格当前从 30 元/万次开始。
- 商业发布还需要遵守高德服务协议、认证和具体场景许可，不能只根据“有免费配额”判断可以无限商用。

官方资料：

- [高德开放平台基础服务计费说明](https://lbs.amap.com/pages/base_service_price)
- [高德地图技术服务使用许可协议](https://lbs.amap.com/pages/authorization/)
- [高德路径规划 API](https://lbs.amap.com/api/webservice/guide/api/direction)

### 9.2 Mapbox 地图与 Directions

- Mapbox 采用免费额度 + 超额计费，不是无限免费。
- Mapbox GL JS 地图加载当前每月前 50,000 次免费；下一档为 5 美元/1,000 次加载。
- Directions API 当前每月前 100,000 次请求免费；100,001 至 500,000 次为 2 美元/1,000 次请求，之后阶梯下降。
- 一次包含多个途经点的 Directions 请求按一次请求计费，但普通 Directions 最多支持 25 个坐标点，并受 300 请求/分钟等限制。
- 对求职 Demo 和早期低流量产品，免费额度通常够用；上线后必须增加用量告警和预算上限。

官方资料：

- [Mapbox Pricing](https://www.mapbox.com/pricing)
- [Mapbox Directions API](https://docs.mapbox.com/api/navigation/directions/)

### 9.3 当前 OSM/ORS 方案的注意事项

- OpenStreetMap 数据开放，但官方公共瓦片服务器不是无限、带 SLA 的免费 CDN；重度使用可能被限制或封禁。
- 当前 OpenRouteService 公共 API 默认 Directions 限额为每天 2,000 次、每分钟 40 次，适合开发和 Demo，不适合无治理地承载高并发生产流量。
- 第一阶段可以保留现有 Provider 抽象与免费服务，但必须增加 Key 配置检查、缓存、限流、失败提示和供应商替换能力。

官方资料：

- [OpenStreetMap Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)
- [OpenRouteService FAQ](https://giscience.github.io/openrouteservice/frequently-asked-questions)

### 9.4 第一阶段地图决策

第一阶段保留并修复现有混合方案：

- 国内使用百度地图 WebGL JS API 和百度 DirectionLite。
- 国际使用 Leaflet、合规 OSM 底图服务和 OpenRouteService。
- 抽象统一 `MapProvider`、`GeocodingProvider` 和 `RouteProvider` 接口，让前端工作台不依赖具体供应商。
- 删除或替换当前直接拼接的非正式高德瓦片地址，不把它作为正式降级方案。
- 增加启动时 Key 配置诊断、用量限制、缓存、失败提示和坐标系一致性校验。
- Mapbox 和高德作为后续可插拔 Provider，不进入第一阶段主链路重写。

## 10. 旅行工作台

### 10.1 P0 功能

- 总览。
- 整体行程备注。
- 分日计划。
- 活动卡片备注/便签。
- 候选池。
- 约束提醒。
- 撤销。
- 地图联动。
- 同日拖拽排序。
- 跨天拖拽。
- 从候选池添加。
- 替换活动。
- 删除活动。
- 智能优化，并在执行前选择允许调整的范围。
- 允许用户手动将活动标记为固定时间。

### 10.2 修改提交方式

用户选择批量编辑模式：

1. 用户可以连续拖拽、跨天移动、添加、替换、删除或填写备注。
2. 编辑期间只更新工作台草稿，不立即调用路线服务，也不覆盖服务器正式版本。
3. 界面持续显示“有未应用修改”，并提供“撤销上一步”和“放弃全部未应用修改”。
4. 用户点击“应用修改”后，系统一次性提交操作集合。
5. 后端基于当前正式快照和操作集合生成新的完整快照，只重新计算受影响日期的路线、时间、预算和约束。
6. 如果某项变更影响住宿、去返程交通、全程预算或其他跨日依赖，后端同时重算对应依赖，但不重新执行与修改无关的完整 Agent 规划流程。
7. 后端始终输出一份新的完整行程 Schema；校验通过后以事务方式把原当前快照移动为“上一次正式版本”，再写入新的当前正式快照，并递增并发控制用的 `revision`。每个行程最多保留当前和上一次两份正式版本，不形成版本列表。
8. 前端根据新 Schema 确定性地整体重新渲染中间规划、地图和工作台，同时保持用户原有滚动位置，并短暂高亮发生变化的日期和卡片。
9. Agent 过程区域只追加一条可折叠的“本次修改摘要”，显示修改内容、重算范围、数据源、校验结论和耗时，不复制首次生成时的完整多 Agent 过程。
10. 校验失败时返回具体冲突，保留用户草稿，由用户选择继续修改、忽略非致命警告或放弃。

- 工作台存在未应用草稿时，如果用户又通过中间对话请求修改行程，输入框上方显示行内冲突提示，不使用强制弹窗。
- 用户可以选择“先应用工作台修改，再发送请求”“放弃工作台草稿并发送”或“取消”；系统不能静默合并两个入口产生的修改。

需要防止：

- 多次点击“应用修改”造成重复提交或重复递增 `revision`。
- 编辑期间收到旧的异步路线结果覆盖新草稿。
- 跨天移动后只改卡片、不更新日期预算和地图路线。
- 修改失败后整个行程丢失。

### 10.3 候选池与修改校验

- 活动具有 `scheduled`、`candidate` 和 `deleted` 等明确状态。
- 用户不喜欢某个已安排活动时，可以将其从某一天拖入候选池；这不是删除，也不是数据错误。
- 候选活动不需要归属某一天，因此“活动不属于任何一天”不能作为阻止保存的条件。
- 进入候选池后保留地点、图片、简介、来源、备注、参考价格和原所在日期，方便用户稍后拖回日程。
- 候选活动不参与正式日程的路线、时间冲突、每日预算和全程预算计算。
- 用户点击“应用修改”后，只对 `scheduled` 活动进行分日路线和时间校验。
- 硬阻止条件包括版本已过期、旅行日期无效、已安排活动缺少日期、结束时间早于开始时间、固定时间活动直接重叠或结构化数据损坏。
- 超预算、营业时间风险、预约未核验、通勤过长、天气风险和真实路线失败属于非致命警告；用户确认“仍然应用”后可以替换当前正式快照。
- 候选池属于当前旅行并随当前正式快照保存，不是跨行程共享的收藏夹，也不按日期拆分。
- 同一个 POI 在当前行程中只有一个活动实例，通过 `scheduled` 与 `candidate` 状态切换，不能在候选池和正式日程中产生重复副本。
- 地图默认隐藏候选点；用户开启“显示候选”后，使用区别于正式日程的浅色标记显示候选地点。
- 候选活动可以拖回任意一天，也可以彻底删除；应用修改前可撤销最近一步草稿操作，应用后可恢复到上一次正式版本。

### 10.4 活动卡片信息密度

- 右侧工作台活动卡片以快速浏览和拖拽编辑为目标，不承载完整的数据核验信息。
- 卡片只展示与规划直接相关的简要内容，例如图片、名称、简短描述、建议时间、营业时间、参考票价、餐厅特色菜或人均消费。
- 总览区域提供整趟行程备注；每张活动卡片提供自己的备注入口，备注与稳定 `activity_id` 绑定，活动在日期和候选池之间移动时不得丢失。
- 桌面端允许用户直接在活动卡片中编辑计划开始时间和结束时间；修改先进入工作台草稿，点击“应用修改”后才进行冲突校验并保存。
- 时间选择器以 15 分钟为步长，并允许键盘直接输入有效时间。
- 结束时间早于开始时间、超出当天范围或与固定时间活动重叠时立即显示行内错误；普通活动之间的时间冲突可以继续调整，但点击“应用修改”前必须解决。
- 固定时间活动发生冲突属于硬阻止条件，不能通过“仍然应用”绕过。
- 卡片不展示来源状态标签、最后核验时间和数字引用角标，也不提供重新核验价格、库存或预算的按钮。
- 中间最终规划仍保留数字角标和底部完整参考来源列表，满足信息可追溯要求。

### 10.5 正式方案稳定性、优化范围与固定约束

- 用户在工作台点击“应用修改”后保存的排列就是新的当前正式方案；后续 Agent 不得在没有用户发起优化的情况下主动重排。
- 用户通过对话提出“优化一下路线”，或点击“智能优化”时，系统先询问本次允许调整的范围：
  1. 保持当前地点和日期，只优化同一天内的顺序、交通与时间。
  2. 保持用户手动调整过的活动不变，只补充时间空档。
  3. 允许全面重新规划。
- 每次智能优化都由用户主动确认优化范围；第一项作为默认推荐项，但系统不能因为存在默认项而跳过确认直接执行。
- 第一阶段不提供通用“锁定活动”功能，减少额外状态和用户理解成本。
- 当前产品只负责规划行程，不能假设用户已经购票或完成预约，因此不根据推荐结果自动创建“已购票”“已预约”等固定状态。
- 用户可以手动将某个活动标记为 `fixed_time_constraint`；标记时使用活动卡片中当前计划时间，总控 Agent 和路线规划 Agent 在后续优化中必须优先满足该时间约束。
- 用户发起智能优化时，范围确认卡明确提醒“优化可能调整未固定活动的时间”；用户不希望某个活动时间变化时，可以先在活动卡片中将其标记为固定时间。
- 用户编辑、移动、替换或删除手动固定时间的活动时，系统必须先明确提示可能造成的时间冲突，再由用户确认是否继续。
- “只补充时间空档”时优先从当前候选池选择距离、时间和预算合适的活动；候选池没有合适内容时保留休息或自由活动，不自动调用 Agent 搜索新地点。

### 10.6 工作台与地图双向联动

- 点击活动卡片后，地图居中并高亮对应地点标记和相关路线段。
- 点击地图标记后，工作台切换到对应日期并滚动到活动卡片；桌面端悬停只做轻量高亮，移动端使用点击联动。
- 拖拽期间只更新工作台顺序编号和地图地点序号，不调用真实路线服务，也不让旧路线结果覆盖草稿。
- 用户点击“应用修改”后，后端才重新计算受影响日期的真实路线，成功后地图切换到当前最新 `revision` 的路线结果。

## 11. 预算和费用

已确认：

- 创建行程时由用户填写全程总预算，第一阶段不要求填写各消费类别上限。
- Agent 自动给出交通、住宿、餐饮、门票和其他费用的参考分配。
- 营业时间、票价和人均消费跟随具体景点或餐厅展示。
- 每天结束处可以显示当日费用小计。
- 全部日程结束后显示整个旅程费用汇总。
- 每项金额只标记为“参考价格”；用户需要前往对应平台对比和确认实际价格。
- 强实时金额查询失败时明确提示用户自行核验，不能用模型估算冒充真实价格。
- 第一阶段不做实际消费记账。
- 预算是软约束：无论预计费用是否超过预算或总容差，都继续生成完整规划行程。
- 规划器仍应优先尝试贴近用户预算，不能因为允许超出就主动推荐无必要的高消费方案。
- 用户人均预算低于 2,000 元时，每人参考容差为 300 元；人均预算达到或超过 2,000 元时，每人参考容差为 500 元。
- 成人、儿童和老人第一阶段都按一个人计算预算容差；只有查到可靠优惠信息时，才在具体费用中计算儿童或老人优惠。
- 查到官方或可靠渠道明确公布的儿童、老人优惠时，分别展示对应价格并参与团队预算计算。
- 无法确认儿童或老人优惠时，暂按成人价格进行保守预算，并在相关费用项标记“儿童/老人优惠待确认”，避免低估预计总费用。
- 预计费用未超预算时正常展示；超过预算但处于总容差内时显示轻量提醒；超过总容差时显示醒目预算警告，但不阻止完整行程生成。
- 预算警告需要说明参考总费用、预算差额和主要超支类别，并提供降低住宿标准、替换高价活动、调整交通或缩短天数等建议。
- 预算区域始终提醒：“以上为参考价格，实际花费请以用户真实查询和消费为准。”
- 国际旅行同时保留当地原币和人民币参考换算，并在金额后明确写出货币单位，例如 `€32 欧元（约 ¥252 人民币）`。
- 汇率每天更新并缓存一次，显示汇率来源和更新时间；查询失败时只展示当地原币，不使用模型猜测换算结果。
- 价格只补充对理解有帮助的计价对象，例如 `/成人`、`/儿童`、`/人`、`/间` 或 `/程`；不重复添加上下文已经明确的“单程”“单晚”等常识性文字。
- 推荐格式示例：火车票 `¥320 人民币/成人`、酒店 `¥680 人民币/间`、餐厅 `¥85 人民币/人`、打车 `约 ¥42 人民币/程`、国际门票 `€32 欧元/成人（约 ¥252 人民币/成人）`。
- 每日小计和全程总计表示整个同行团队的参考总价，只显示币种与金额，不添加 `/人`。

## 12. 图片策略

- 城市封面优先使用 Unsplash。
- 景点和餐厅图片优先使用地图服务、官方网站或可靠网络来源。
- 图片必须保存来源、更新时间和授权/署名信息。
- 无可靠图片时展示一致的占位内容，不使用模型生成图片冒充真实景点照片。
- 工作台卡片、Agent 最终方案、聊天内容和地图弹层采用各自固定尺寸和宽高比，统一处理加载失败；父容器设置明确最大尺寸与溢出裁切，图片不得改变三栏宽度或撑高活动卡片。
- 正文与活动卡片不单独展示图片来源标签，避免干扰阅读；来源、授权与更新时间保留在后台元数据中，并在来源许可要求时合并到文末参考来源或导出附录。

## 13. 下载与移动端

### 13.1 下载

- 第一阶段支持 Markdown 和 PDF。
- 不实现分享链接。
- 下载内容应来自当前已保存的正式行程版本，而不是尚未应用的工作台草稿。
- PDF 和 Markdown 只包含面向旅行者的最终规划、预算、提醒、参考来源和地图链接，不导出 Agent 规划过程。
- PDF 在路线静态图可可靠生成时加入分日路线图；无法生成时保留可点击地图链接，不使用伪造路线图替代。
- Markdown 的参考来源可以使用可折叠 `<details>`；PDF 是静态文档，参考来源固定放在文档末尾。
- 导出始终基于最新已保存正式快照；相同 `trip_id + revision + format` 的生成结果临时缓存 10 分钟，避免连续点击重复生成，过期后自动清理。
- 存在未应用工作台草稿时，下载入口提供“先应用修改再下载”“下载当前已保存版本”和“取消”，不能静默把草稿混入导出文件。
- 默认文件名格式为“目的地_起止日期_旅行计划.md”或“目的地_起止日期_旅行计划.pdf”。

### 13.2 移动端

- 采用响应式 Web，不开发原生 App。
- 支持查看历史、最终规划、地点和地图。
- 只支持添加/编辑备注、标记或取消固定时间、在当天使用“上移/下移”调整顺序，以及删除活动。
- 第一阶段移动端不支持跨天移动、候选池调度、替换活动或直接编辑活动时间。
- 不要求移动端拖拽。
- 复杂地图和工作台通过标签页或抽屉切换，避免三栏内容强行压缩。

## 14. 数据持久化与单级版本恢复

- 浏览器生成匿名设备标识，通过安全 Cookie 或本地令牌关联后端记录。
- 后端 SQLite 保存旅行、对话摘要、当前正式行程快照、上一次正式快照、工作台草稿/操作集、引用和当前导出记录。
- 每个行程最多保留“当前正式版本 + 上一次正式版本”两份快照，不提供历史版本列表。
- 每次“应用修改”在同一个事务中把原当前版本写入上一版本槽位、保存新当前版本并递增单调 `revision`；更早的正式版本立即被覆盖。

- 同一批次尚未提交的操作只支持撤销最近一步草稿操作；应用成功后提供“恢复上一次正式版本”。恢复时把上一版本内容复制为新的当前版本并分配新的单调 `revision`，删除被撤销的新版本并清空上一版本槽位，不提供重做。

- 对话、行程和技术日志禁止保存身份证/护照号码、银行卡、支付密码、账户密码、完整订单号和预约验证码；检测到用户输入此类内容时进行提醒，并在进入技术日志前脱敏。
